Hybrid LLM Merge Architecture + Results

1) Recommended Architecture (Hybrid)

Input mini-graphs -> deterministic merge (high precision baseline) -> embed events (retrieval layer) -> candidate pair pruning (top-k + threshold) -> LLM linker (same_event + temporal + causal) -> strict validation (schema + endpoint checks) -> union-find identity dedupe -> remap edges + provenance fields -> final merged graph + audit metrics + HTML visualization

Why this is better: deterministic stage keeps precision; retrieval controls LLM cost; LLM adds semantic cross-chunk links that rules miss.

2) Speech Script (Presentation)

We start with a deterministic merge so we always have a stable, reproducible baseline. Then we compute embeddings for merged events and only keep high-similarity candidates. This reduces LLM calls while preserving likely cross-chunk matches. For each candidate, the LLM returns three decisions: identity, temporal relation, and causal relation. We validate outputs strictly, apply union-find for identity merges, remap edges, and store provenance for auditability. This design gives us precision from rules and recall from semantic linking.

5) Hybrid speech (what to say)

Our hybrid merger has two layers: deterministic merge for stability, then LLM refinement for semantic links. We first merge entities and events with strict rules, so we preserve precision and reproducibility. Next, we embed events and keep only high-similarity candidates to control LLM cost. The LLM then decides same-event identity and temporal or causal links, and we only accept outputs that pass schema and endpoint validation. On this sample, retrieval generated 13 candidates across five documents. The LLM path is operational but the current runtime had a connection error in the 1-document test, so we report zero LLM-added links in these results.
